# Repository audit: Riemann Zeta Computational Observatory

_Date of audit: 2026-05-07_

> **Status note (2026-05-07):** This audit is retained as historical context from an earlier repository state. The repository now includes an installable `riemann_lab/` package, `pyproject.toml`, tests, and updated user-facing documentation. Some observations below may therefore describe pre-refactor conditions rather than the current architecture.

## 1. Purpose and audit boundary

This is an audit-only review of the current repository state. It does **not** implement the proposed package architecture, refactor scripts, delete files, change scientific claims outside this document, or reorganize the repository.

The target identity proposed by the project owner is **Riemann Zeta Computational Observatory**: a reproducible computational laboratory for sober exploration of the Riemann zeta function, non-trivial zeros, the critical line, finite numerical verification, prime-counting functions, zero-spacing statistics, visualizations, and carefully labelled analogies or exploratory machine-learning experiments.

The guiding scientific constraint for all future work should be:

> Numerical computation can illustrate and verify finite cases; it cannot prove the Riemann Hypothesis. Random-matrix, quantum-chaos, and machine-learning material must be presented as analogy, comparison, or exploratory modelling, not as evidence for a proof.

## 3. Main technical problems

### 3.1 No importable package boundary

There is no `riemann_lab/` package, no `pyproject.toml`, and no tested public API. Reusable functions exist, but they are mixed with immediate script execution. For example:

- `compute_zeros/zeta_zeros.py` computes `N = 100` zeros at module import/run time and writes output immediately.
- `prime_distribution/prime_count.py` defines a useful sieve function, then immediately runs a demo.
- `prime_distribution/riemann_approx.py` reads a generated file at import time before defining and running the approximation.
- `machine_learning/data_preparation.py` and `machine_learning/lstm_model.py` perform file I/O and training as top-level side effects.

This makes reuse, testing, and composition difficult.

### 3.2 Fragile path handling

Several scripts use relative paths that depend on the current working directory rather than the script location or repository root:

- `prime_distribution/riemann_approx.py` opens `../compute_zeros/results/zeros_found.txt`.
- `quantum_connections/zeros_spacing.py` opens `../compute_zeros/results/zeros_found.txt`.
- `theoretical_approaches/de_bruijn_newman.py` opens `../compute_zeros/results/zeros_found.txt`.
- `quantum_connections/visualizations/spacing_comparison.py` loads `../visualizations/*.txt`.
- `prime_distribution/visualizations/prime_error_plot.py` loads `error_data.txt` from the current directory.
- `docs/scripts/*.py` save to `images/...`, which means output goes to `./images` unless the scripts are launched from `docs/`.

Future code should resolve paths through a single utility module and should separate source files, input data, caches, and generated outputs.

### 3.3 Broken or missing imports

Known import problems include:

- `prime_distribution/ulam_spiral.py` imports `utils.plot_utils`, but no `utils/` package exists.
- `notebooks/Explore_Riemann_Hypothesis.ipynb` imports `utils.zeta_utils.compute_zeros` and `utils.plot_utils.set_plot_style`, but neither module exists.
- `prime_distribution/error_analysis.py` imports `prime_count` and `riemann_approx` as sibling modules; this only works under some launch contexts and is not package-safe.

A syntax-only compilation pass currently succeeds, but that does not validate runtime imports or required generated data.

### 3.4 Duplicated code and concepts

The same ideas appear in multiple places with slightly different implementations:

- Zero computation appears in `compute_zeros/zeta_zeros.py`, `visualizations/zeros_plot.py`, `docs/scripts/plot_zeros_critical_line.py`, and the notebook.
- Zero parsing appears in `compute_zeros/verify_critical_line.py`, `machine_learning/data_preparation.py`, `prime_distribution/riemann_approx.py`, `quantum_connections/zeros_spacing.py`, and `theoretical_approaches/de_bruijn_newman.py`.
- Prime sieving appears in `prime_distribution/prime_count.py`, `docs/scripts/plot_prime_counting.py`, and the notebook.
- Zeta grid evaluation appears in `visualizations/domain_coloring.py`, `visualizations/zeta_function_3d.py`, `docs/scripts/plot_domain_coloring.py`, `docs/scripts/plot_zeta_magnitude.py`, the Dash app, and the notebook.
- Spacing statistics appear in `quantum_connections/zeros_spacing.py`, `docs/scripts/pair_correlation.py`, and the notebook.

These should eventually be consolidated into package functions, with scripts and notebooks calling the same implementation.

### 3.5 Missing tests and quality gates

There is no `tests/` directory and no test runner configuration. Missing test categories include:

- Unit tests for zero parsing and serialization.
- Unit tests for prime-counting values such as `π(10)=4`, `π(100)=25`, `π(1000)=168`.
- Regression tests for known imaginary parts of the first several zeta zeros.
- Tests that verification correctly distinguishes “finite numerical check” from proof-like language.
- Tests for path handling from repository root and from subdirectories.
- Smoke tests for CLI commands, plotting commands with non-interactive backends, and the Flask calculator.

### 3.6 Dependency and reproducibility problems

`requirements.txt` is unpinned and includes heavyweight optional dependencies such as TensorFlow, Dash, Flask, Jupyter, and Pillow in one flat environment. This makes installation slower and less reproducible than necessary. Future work should separate core numerical dependencies from optional groups such as `viz`, `web`, `ml`, and `notebooks`.

No Python version is specified. No lock file, no deterministic random seeds for ML, and no environment metadata are recorded for generated figures.

### 3.7 Performance and precision problems

- Dense nested loops call `mpmath.zeta` one grid point at a time; this is acceptable for small educational plots but should be clearly labelled and parameterized.
- Precision is mostly implicit. `mpmath.mp.dps` is not centrally controlled except in `theoretical_approaches/de_bruijn_newman.py`.
- `compute_zeros/zeta_zeros.py` hard-codes `N = 100`.
- `docs/scripts/pair_correlation.py` computes 1000 zeros with no caching or CLI controls.
- The explicit-formula approximation in `prime_distribution/riemann_approx.py` is mathematically too informal for a serious package and may be numerically unreliable for complex logarithmic integrals and truncation handling.

### 3.8 Web and dashboard safety/ergonomics

`web_calculator/app.py` and `visualizations/dashboard/app.py` run in debug mode by default when executed directly. That is acceptable for local educational use but should be documented as local-only and made configurable in future.

## 4. Main mathematical and scientific documentation problems

### 4.1 README claim audit

The current `README.md` is generally cautious and explicitly says the project does not claim a proof. It also says ML scripts should not be interpreted as evidence for or against RH. That is good and should be preserved.

However, some wording should be tightened in a future documentation pass:

- “Numerical agreement for the first `N` zeros is evidence for those samples only” is mostly safe, but “verification for those finite samples” is better than “evidence” to avoid rhetorical overreach.
- “Connect classical number theory ideas with modern computational tooling” is fine.
- “Random-matrix / quantum-chaos analogies” is appropriately cautious in the README, but not always as cautious in the notebook and script titles.

### 4.2 Notebook overclaim and staleness audit

The notebook contains the most visible scientific-documentation risks:

- It imports missing `utils` modules, so it is not reproducible as written.
- It says the pair correlation “matches the GUE prediction” after computing only a finite sample in a simplified demonstration. This should be replaced by wording such as “can be compared visually with the GUE pair-correlation prediction.”
- It discusses “connections to fields like quantum physics” and Hilbert-Pólya ideas. That is appropriate only if clearly marked as conjectural motivation/analogy, not evidence.
- It refers to `CONTRIBUTING.md`, which does not exist.
- It ends with “PiSequenceExplorer,” which appears to be a stale project-name remnant.

### 4.3 Theoretical approach risks

`theoretical_approaches/de_bruijn_newman.py` is the highest-risk scientific script. It claims to “estimate the de Bruijn-Newman constant” using a simplified zero-movement model. In its current form it should not be presented as a reliable numerical estimate. Future documentation should mark it as an obsolete toy model or replace it with a carefully sourced exposition and, if desired, a clearly labelled demonstration that does not produce estimate-like language.

`theoretical_approaches/literature_review.md` is more careful, but references in both `docs/references.bib` and the literature notes require manual bibliographic review. In particular, entries marked “forthcoming,” website years, and article metadata should be checked against primary sources before being presented as authoritative.

### 4.4 Machine-learning framing risks

The ML workflow trains an LSTM to predict zero ordinates from previous ordinates. This is acceptable as an exploratory sequence-modelling exercise only. Future text should explicitly state:

- It is not evidence for RH.
- It does not discover new mathematics.
- It is trained on values already generated by `mpmath`/known algorithms.
- It should be evaluated as interpolation/extrapolation behaviour on a deterministic sequence, not as theory.

### 4.5 Prime-distribution framing risks

The repository should distinguish:

- Known theory: Prime Number Theorem, explicit formulas, relationship between zeros and error terms.
- Numerical experiment: computed `π(x)` values and approximations over finite ranges.
- Visualization: plots of `π(x)`, `Li(x)`, and errors.

Future code and docs should avoid implying that simple plots of `π(x)` versus `Li(x)` provide evidence for RH.

### 4.6 Random-matrix / quantum-chaos framing risks

The repository may discuss Montgomery pair correlation, GUE statistics, and Hilbert-Pólya motivation, but future docs should carefully separate:

- rigorous theorems and conjectures;
- empirical numerical comparisons;
- analogy with quantum-chaotic systems;
- speculative physical interpretations.

The current `quantum_connections/quantum_chaos.py` is a simplified perturbed-rectangle finite-difference calculation, not a faithful stadium billiard implementation. Its output should not be described as a rigorous quantum-chaotic model.

Recommended package boundaries:

- `zeta.evaluation`: safe wrappers for `mpmath.zeta`, precision configuration, grid evaluation.
- `zeta.critical_line`: evaluation of `ζ(1/2 + it)`, sampling utilities, Hardy Z-function support if added later.
- `zeros.compute`: zero retrieval/computation through `mpmath.zetazero`, optional caching, serialization.
- `zeros.verify`: finite numerical checks against tolerances and reference tables, with explicit non-proof language.
- `zeros.spacing`: spacings, normalized spacings, unfolding helpers, pair-correlation inputs.
- `primes.counting`: sieve implementations and prime-counting functions.
- `primes.approximations`: `Li(x)` and carefully documented explicit-formula approximations.
- `statistics.distributions`: histograms, empirical CDFs, summary statistics.
- `statistics.random_matrix`: GUE/Wigner-surmise comparison curves, labelled as statistical analogy/comparison.
- `visualization.plots` and `visualization.heatmaps`: plotting functions that accept data and axes; no hidden file reads.
- `experiments.runners`: reproducible experiment definitions with config, output paths, metadata, and seeds.
- `utils.precision`, `utils.paths`, `utils.validation`: central precision, path, and input-validation tools.

## 7. Suggested CLI design

The future CLI should be thin: parse user arguments, call package functions, write explicit outputs, and print sober summaries.

Proposed commands:

```bash
python -m riemann_lab zeros --count 100 --precision 50
python -m riemann_lab verify --count 100 --tolerance 1e-10
python -m riemann_lab plot zeros --count 100
python -m riemann_lab plot zeta-heatmap --real-min -2 --real-max 2 --imag-min 0 --imag-max 40
python -m riemann_lab primes --limit 100000
python -m riemann_lab spacing --count 1000
```

Recommended CLI principles:

- Every command should support `--output` or write to a documented default under `outputs/`.
- Commands that compute zeros should record precision, library versions, count, timestamp, and parameters.
- Verification commands should print “finite numerical verification” rather than “proof” or “confirmation of RH.”
- Plot commands should be able to run headlessly, e.g. with Matplotlib `Agg`, and should not call `plt.show()` unless requested.
- Expensive commands should expose count/range/precision controls and optional cache paths.
- ML commands, if kept, should live under an explicitly labelled `experiments ml` namespace and print a non-evidence warning.

## 9. Suggested visualization structure

Visualization code should be separated from numerical computation:

- Plotting functions accept arrays/dataframes and optional Matplotlib axes.
- Script/CLI wrappers compute or load data, then call plotting functions.
- All generated figures should include enough metadata to reproduce the inputs.
- Documentation figures should be regenerated by one documented command, for example `python -m riemann_lab docs build-figures` or a Make/Nox task.
- Interactive apps should reuse the same computation layer as static plots.

Suggested future visualization groups:

| Visualization | Future owner |
|---|---|
| First zeros on the critical line | `visualization.plots.plot_zeros` |
| `|ζ(σ+it)|` heatmaps | `visualization.heatmaps.plot_zeta_magnitude` |
| Domain coloring | `visualization.heatmaps.plot_domain_coloring` |
| Prime-counting comparison | `visualization.plots.plot_prime_counting` |
| Zero-spacing histogram | `visualization.plots.plot_spacing_histogram` |
| GUE comparison curves | `statistics.random_matrix` for curves, `visualization.plots` for display |
| Web calculator and Dash dashboard | Small apps calling `riemann_lab` APIs |

## 10. Suggested test strategy

### 10.1 Unit tests

- `zeros.compute`: first-zero ordinates match reference values within configured tolerance.
- `zeros.verify`: rejects zeros with real part outside tolerance; handles empty inputs.
- `zeros.parse`: parses current text format and future structured formats.
- `primes.counting`: validates `π(x)` for standard small values.
- `primes.approximations`: checks basic domain handling and monotonic sanity for simple approximations.
- `statistics`: validates spacing normalization and histogram input handling.
- `utils.paths`: validates output path creation from repository root and subdirectories.

### 10.2 Integration and smoke tests

- Run `python -m riemann_lab zeros --count 10 --precision 50` into a temporary directory.
- Run finite verification on the generated output.
- Generate one small heatmap with a non-interactive backend.
- Start Flask/Dash apps only through lightweight import tests unless explicit web-app testing is added.
- Execute notebooks with `nbmake` or an equivalent tool after package APIs exist.

### 10.3 Scientific text checks

Add documentation-review checks for forbidden or high-risk phrases. Examples to flag for manual review:

- “proves RH”
- “confirms the Riemann Hypothesis”
- “ML evidence”
- “zeros match GUE” without “finite sample” or “comparison” context
- “estimated de Bruijn-Newman constant” unless tied to a rigorous, cited computation

These checks should not replace human review, but they can catch accidental overclaiming.

## 12. Risks and manual review points

### 12.1 High-priority risks

- The de Bruijn-Newman script may be mistaken for a real estimate; it needs immediate cautionary framing or replacement in a future task.
- The notebook is not currently reproducible because of missing `utils` imports and stale project references.
- The explicit-formula approximation is mathematically under-specified and may produce misleading outputs if presented without truncation/error caveats.
- Relative-path assumptions will cause scripts to fail or write outputs in unexpected locations.
- Heavy dependencies make onboarding difficult and may block simple use cases.

### 12.2 Manual review points

- Review `docs/riemann_hypothesis.pdf` for proof-like language, stale project identity, reference quality, and reproducibility claims.
- Verify every entry in `docs/references.bib`; do not keep uncertain “forthcoming” or date-sensitive metadata without checking primary sources.
- Decide whether generated PNGs should remain versioned documentation artifacts or be regenerated in CI/docs builds.
- Decide whether the web calculator is part of the target scientific lab or an optional educational demo.
- Decide whether ML belongs in the main repository or in a clearly separated optional appendix/experiment.
